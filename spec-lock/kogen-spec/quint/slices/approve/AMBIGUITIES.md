# Ambiguities in PROSE.md and what the spec chose

1. **Order of refusals.** The prose lists steps but not where each refusal sits. Chosen: `--by` invalid, then (hash given only) acceptance file missing, hash mismatch; then parse, lint, (no hash) acceptance missing, identity, setup, baseline, acceptance check, then card / witness check / write. Reasoning: "compute the hash first" needs both files, so with a hash a missing test is hit before the mismatch; without a hash the prose order is parse, lint, read the test.
2. **When the git identity is checked.** Prose only says Approver is on the card and that no identity is exit 2. Chosen: after lint, before setup/checks, on both the card call and the approval call; skipped when `--by` is given.
3. **Hash prefix.** "`<prefix>`" and "`<sha8>`" are both mentioned; the accepted length is unstated. Chosen: the adapter decides `prefixOk` (the argument is a prefix of the full hash); the spec only sees a boolean. An empty hash argument means "no hash".
4. **Witness mode details.** "without a PROVEN witness" vs verdict `PROVEN_WITH_CONCERNS`. Chosen: both PROVEN and PROVEN with concerns pass; UNPROVEN and "not checked" refuse. The check happens only on the hash call, after the acceptance check, so the card (exit 5) is still printed in witness mode with an unproven Intent. Whether the baseline/acceptance run before the witness check is a guess (they do).
5. **Is the baseline run when the acceptance check is red?** Step 2 precedes step 3, so yes, and it is cached. Is it cached when setup fails or lint fails? No (never reached).
6. **Are red-baseline and lint-style warnings shown on the approved output?** Prose: "warnings first". Chosen: both lint warnings and the red-baseline warning are shown on card and approval, from the same inputs (the baseline status is the cached one).
7. **Baseline statuses.** Only `red` warns; `unavailable`, `timeout`, `mutating`, `green` do not. Unstated.
8. **Cache scope.** "cached by (base tree, setup, checks, child env)": modelled as one opaque `cacheKey` and a single-entry cache (a new key replaces the old one). Real cache may hold several entries; a key flip-flop (k1, k2, k1) differs between a single-entry and multi-entry cache. Chosen: single entry.
9. **Setup runs every call** (it is not cached; only the baseline is). Setup failure is not modelled as touching the cache.
10. **Acceptance outcomes.** red and timeout both give `check/acceptance_check_failed` exit 1; 126/127 give `environment/tool_missing` exit 3 (the prose also lists `environment/tool_missing` only generally, I assumed it is the code for 126/127).
11. **Invalid `--by`** (blank / multi-line): prose says "non-blank, one line" but gives no error line. Chosen: code `usage`, exit 2 ("a request the caller fixes by changing arguments").
12. **Outcome codes** for success (`ok`) and card (`needs_decision`) are my own names; the prose only gives exit codes 0 and 5. Error codes are the prose strings verbatim.
13. **Not modelled** (silent or out of slice): intent not found / untracked (exit 2), unreadable request, `--force`, the write CAS retry and lost race, ledger.json, manifest contents, queueing, the exact card text and the <=20 / <=5 line truncations. Whether a card call changes persisted state: chosen no (only the baseline cache).
14. **Re-approval** with an identical hash: modelled as always writing a new commit (n+1); the prose says so ("writes a new approval commit"), but whether an unchanged Intent is a no-op is silent.
15. **Mismatch message** uses the real hash's sha8; I expose it as `sha8` in the observation.
